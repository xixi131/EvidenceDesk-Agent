# ADR-003｜采用浅层模块化单体与基础设施适配器分层

- 状态：Accepted
- 日期：2026-08-06
- 决策人：tangxitao（Codex 辅助分析）

## 背景

项目已经完成 FastAPI、统一错误、request_id、日志、Docker Compose、PostgreSQL/Weaviate 就绪检查和基础 CI，开始进入真实 RAG 数据处理。现有规划虽然按 `api`、`rag`、`database` 等目录划分，但仍存在两个风险：

1. API Router 直接调用外部依赖探测代码，应用用例编排边界不清晰；
2. Embedding、Weaviate、GitHub REST、PostgreSQL 等外部实现可能继续散落到 RAG、Tool 和 Database 模块，后续难以替换 Fake 或定位外部故障。

同时，项目是学习驱动的第一版模块化单体，不能为了形式复制多层 Clean Architecture，形成 `domain/service/port/adapter/impl` 等过深目录。

## 约束

- 业务约束：第一版必须保持 GitHub Actions 技术支持和工单协同主线；
- 技术约束：FastAPI、LangGraph、PostgreSQL、Weaviate 和 GitHub REST API 的职责已冻结；
- 时间约束：当前需要继续推进 RAG，不进行大规模无业务价值重写；
- 学习约束：目录必须能帮助用户理解依赖方向，而不是隐藏真实数据流；
- 结构约束：默认目录深度不超过 `evidence_desk/<模块>/<子模块>/<文件>.py`。

## 候选方案

### 方案 A｜继续保持扁平目录

优点：

- 文件少；
- 初期开发速度快。

缺点：

- Router、RAG 和 Tool 容易直接调用数据库或 HTTP Client；
- 外部适配代码与业务规则混在一起；
- 后续 Fake、重试、限流和错误映射难以复用。

### 方案 B｜完整 Clean Architecture / DDD 多层目录

优点：

- 理论边界严格；
- 适合大型团队和复杂领域。

缺点：

- 第一版会出现大量 Port、Adapter、DTO、Mapper 和空目录；
- 调用链过长，增加学习和排错成本；
- 当前业务规模不足以证明这些层次的价值。

### 方案 C｜浅层模块化单体

优点：

- 顶层按能力划分；
- Application 只做用例编排；
- Infrastructure 集中外部 I/O；
- RAG、Agent、Tools 保留真实业务逻辑；
- 只在出现 Fake、第二实现或稳定文件族时增加子目录。

缺点：

- Application 在早期仍可能只有少量用例；
- 部分模块随着规模增长仍需二次拆分；
- 需要持续检查 import 方向。

## 决策

选择方案 C：浅层模块化单体。

顶层模块固定为：

```text
api
application
rag
agent
tools
infrastructure
evaluation
core
```

职责：

- `api`：HTTP 输入输出和依赖注入；
- `application`：用例编排、事务边界和应用级结果；
- `rag`：可测试的文档处理、分块、检索规则和引用逻辑；
- `agent`：LangGraph State、Node、Route、终止和恢复；
- `tools`：Tool 参数、策略和业务语义；
- `infrastructure`：PostgreSQL、Weaviate、GitHub、Embedding Runtime 等外部实现；
- `evaluation`：数据集、指标、实验运行和报告；
- `core`：配置、日志、错误和 ID 等跨模块基础能力。

`main.py` 作为 Composition Root，负责创建并连接 Application Service 和 Infrastructure Adapter。

## 选择理由

该方案直接解决：

- Router 不再承载外部依赖检查和业务编排；
- RAG 模块不直接管理数据库 Session、Token 或外部 Client；
- GitHub/Weaviate/PostgreSQL 错误可以在 Infrastructure 层统一映射；
- 测试可替换 Application Service 或外部检查器；
- 保持最多一层必要子包，避免出现十几层目录。

## 代价和风险

- 现有就绪检查需要从 `core` 移到 `infrastructure`；
- 需要增加少量 Application Service 和 FastAPI 依赖注入代码；
- 如果没有持续约束，`application` 或 `infrastructure` 仍可能变成新的杂物目录；
- 不能因为有 Infrastructure 层就提前创建所有外部适配器。

## 验证方法

- API Router 不直接导入 `psycopg`、`httpx`、Weaviate Client 或 GitHub Client；
- `main.py` 负责组装 `ReadinessService` 和真实依赖探测；
- 自动化测试可替换 Application Service，不需要真实 Docker；
- Ruff、mypy、pytest 和 GitHub Actions CI 全部通过；
- 新任务开始时只创建当前需要的目录和文件。

## 重新评估条件

出现以下情况时重新评估：

- 单个能力模块超过约 15 个高耦合文件；
- 同一外部能力出现两个以上正式实现；
- 多团队需要独立发布模块；
- 事务和领域规则复杂到需要独立 Domain Layer；
- 当前最多一层子包已经无法表达清晰边界。
