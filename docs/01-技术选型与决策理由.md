# 01｜技术选型与决策理由

> 技术选型的目标不是寻找“最好”的框架，而是选择一组能支持业务目标、方便验证、适合当前能力，并能训练工程判断的工具。

核对日期：2026-08-05。

## 1. 选型原则

每一个技术选择都必须回答四个问题：

1. 它解决了什么具体问题？
2. 为什么不用更简单的方式？
3. 它带来了什么额外成本？
4. 以后在什么条件下应该替换？

## 2. 最终技术栈

| 层 | 选择 | 主要责任 |
|---|---|---|
| 语言 | Python 3.11 | Agent、RAG 与后端实现 |

| API | FastAPI | 对外接口、校验、异常、OpenAPI |
| Agent 编排 | LangGraph | State、Node、Edge、循环、暂停恢复 |

## 3. 为什么使用 Python 3.11

选择理由：

- 当前练习环境已经验证；
- Agent、Embedding、向量库生态成熟；
- 避免为了追最新 Python 版本处理不必要的依赖兼容问题。

不是因为 3.11 永远最好，而是因为项目更需要稳定和可复现。

替换条件：所有关键依赖明确支持更新版本，并且升级能解决实际问题。

## 4. 为什么使用 uv

`uv init --package` 可以创建带 `src` 目录的 Packaged Application，后续通过 `pyproject.toml` 管理依赖，并生成 `uv.lock` 固定版本。

选择理由：

- 初始化结构清楚；
- 依赖和虚拟环境统一管理；
- 安装速度快；
- 锁文件适合 CI 和 Docker；
- 比散落的 `pip install` 更可复现。

代价：需要学习少量 uv 命令。

不选 Poetry：不是因为它不好，而是当前项目没有发布包、复杂多环境等必须使用 Poetry 的需求。

官方资料：[uv Creating projects](https://docs.astral.sh/uv/concepts/projects/init/)

## 5. 为什么 FastAPI 是主入口

选择理由：

- 需要自定义文档导入、评测、工单和反馈接口；
- 可以练习 Router、Schema、Dependency、Middleware、Exception Handler；
- OpenAPI/Swagger 足以代替第一版前端；
- 已经有 FastAPI 学习基础。

代价：要自己处理服务层、数据库和错误结构。

为什么不直接把 LangGraph Agent Server 当主应用：

- Agent Server 适合快速运行图；
- 但会隐藏一部分 API 和持久化工程细节；
- 当前目标是练习后端工程，而不是最快上线。

LangGraph Studio 后续可以作为图调试工具，但生产入口仍由 FastAPI 控制。

官方资料：[FastAPI Bigger Applications](https://fastapi.tiangolo.com/tutorial/bigger-applications/)

## 6. 为什么使用 LangGraph

只有以下真实需求才值得使用：

- 知识、工具、澄清、人工审核之间存在条件路由；
- 证据不足时可能改写查询并重试；
- 高风险 Tool 需要暂停；
- 工具失败后需要恢复；
- 会话需要保存 State。

选择理由：这些需求天然是有状态图，而不是一次 Chain。

代价：

- State 设计错误会导致字段覆盖或消息重复；
- 循环必须有终止条件；
- Checkpointer 与业务数据库需要区分。

不选多 Agent：当前问题可以由一个有清晰节点的图完成。多 Agent 会增加通信、调试和评测难度，却没有真实业务必要。

官方资料：[LangGraph Overview](https://docs.langchain.com/oss/python/langgraph/overview)

## 7. 为什么 LangChain 只作为组件库

使用：

- `Document`；
- Text Splitter；
- Embedding；
- Chat Model；
- Structured Output；
- Tool；
- Retriever 接口。

不把整个业务流程交给预构建 Agent，是因为项目需要显式控制路由和状态。

选择理由：复用成熟适配层，同时保留对数据流的理解。

官方资料：[LangChain Retrieval](https://docs.langchain.com/oss/python/langchain/retrieval)

## 8. 为什么选择 Weaviate

项目同时需要：

- Dense Vector Search；
- BM25 精确关键词检索；
- Hybrid Search；
- metadata filter；
- 可调 `alpha` 权重。

这与错误码、产品型号、自然语言改写共存的技术支持场景吻合。

选择理由：

- 已经有 Weaviate 基础；
- Hybrid 功能直接支持实验；
- 不需要自己实现两套索引服务。

代价：项目需要同时运行 PostgreSQL 和 Weaviate。

为什么不选择 pgvector 作为第一版：

- pgvector 可以减少一个服务；
- 但要自己组合全文检索与向量检索，调试成本更高；
- 当前重点是检索策略和评测，不是搜索引擎底层实现。

替换条件：如果部署资源非常有限，并且数据量较小，可以评估 PostgreSQL + pgvector + 全文检索。

官方资料：[Weaviate Hybrid Search](https://docs.weaviate.io/weaviate/concepts/search/hybrid-search)

## 9. 为什么 PostgreSQL + SQLAlchemy + Alembic

PostgreSQL 保存本项目拥有的业务事实：

- 文档登记与导入任务；
- 支持工单；
- 待审批动作、审批记录和幂等记录；
- Tool 执行审计；
- Prompt 版本；
- 评测运行；
- 用户反馈。

GitHub Workflow Run/Job 的实时状态由 GitHub REST API 提供，不能复制到 PostgreSQL 后当作持续有效的业务真相。

SQLAlchemy 负责：

- ORM Model；
- Session；
- Transaction；
- 查询；
- Repository。

Alembic 负责表结构迁移。

选择 SQLAlchemy 而不是 SQLModel，是为了更完整地练习数据库和事务边界。代价是样板代码更多。

官方资料：

- [SQLAlchemy ORM](https://docs.sqlalchemy.org/en/20/orm/)
- [Alembic](https://alembic.sqlalchemy.org/en/latest/index.html)

## 10. 为什么业务数据库、向量库、外部业务系统和 Checkpointer 分开

```text
PostgreSQL 业务表：保存本项目的工单、审批、审计和评测事实
GitHub REST API：提供 Workflow Run/Job 的实时外部事实
Weaviate：保存可检索的 Chunk 和向量
LangGraph Checkpointer：保存图执行 State
```

不能混用的原因：

- 生命周期不同；
- 查询方式不同；
- 一致性要求不同；
- 清理和迁移方式不同。

PostgresSaver 可以使用同一个 PostgreSQL 实例，但它的数据表由 LangGraph 持久化机制负责，不由业务 Repository 操作。

官方资料：[LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)


## 11. 为什么第一批数据选择 GitHub Actions 中文官方文档

Source Dataset 冻结为 `github-actions-zh-2026-08-05-v1`，共 33 篇渲染后的官方页面 Markdown。数据画像后，Chinese Baseline `github-actions-zh-baseline-v1` 纳入 29 篇，4 篇英文占主导的参考文档留作多语言实验。

选择理由：

- GitHub Actions 的工作流、Job、Runner、日志、缓存、权限和故障排查形成完整技术支持语境；
- GitHub REST API 同时提供只读查询以及取消、重跑等写操作；
- 29 篇中文为主的 Baseline 适合先验证 `bge-small-zh-v1.5`；
- GitHub Docs 内容采用 CC BY 4.0，可保留署名和原始页面 URL 后用于学习、检索与评测；
- 数据已保存固定快照，不依赖运行实验时在线抓取。

代价：

- 文档可能随官方更新，更新必须创建新的 dataset_version；
- 超长 Workflow Syntax 文档增加分块难度；
- 写 Tool 需要 Token，且只能在专用演示仓库验收。

完整决策见 `docs/11-第一版冻结范围与数据集.md`、`docs/12-语料审阅与清洗规则.md`、ADR-001 和 ADR-002。

## 12. 为什么先用轻量 Embedding，再比较强模型

Baseline：`BAAI/bge-small-zh-v1.5`

- 中文；
- 本地运行成本较低；
- 适合快速重建索引；
- 方便建立第一组可重复实验。

实验组：`BAAI/bge-m3`

- 多语言；
- 支持更长输入；
- 可以比较更强模型带来的质量、延迟和资源变化。

先固定分块、top_k 和检索方式，只改变 Embedding，才能判断模型本身的影响。

官方模型卡：

- [bge-small-zh-v1.5](https://huggingface.co/BAAI/bge-small-zh-v1.5)
- [bge-m3](https://huggingface.co/BAAI/bge-m3)

## 13. 为什么先做自定义评测，再接 LangSmith

自定义实现：

- Recall@K；
- Precision@K；
- MRR；
- Route Accuracy；
- Tool 参数正确率。

这能保证自己理解指标，而不是只会点平台按钮。

LangSmith 后续负责：

- Dataset；
- Experiment；
- Evaluator；
- Trace；
- 多版本对比。

代价：需要维护本地数据格式和平台数据的一致性。

官方资料：[LangSmith RAG Evaluation](https://docs.langchain.com/langsmith/evaluate-rag-tutorial)

## 14. 为什么模块化单体，不做微服务

模块化单体能够练习：

- 分层；
- 接口；
- 依赖方向；
- 事务；
- 测试；
- 容器化。

同时避免：

- 服务发现；
- 分布式事务；
- 消息一致性；
- 多服务部署；
- 无意义的网络调用。

只有当某个模块有独立扩容、独立部署或独立团队维护需求时，才拆微服务。
