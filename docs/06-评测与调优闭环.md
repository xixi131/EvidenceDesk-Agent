# 06｜评测与调优闭环

> 调优不是“感觉回答更好了”，而是固定数据、改变一个变量、运行实验、查看失败样例并记录决策。

## 1. 评测分层

```text
数据解析评测
→ 分块评测
→ 检索评测
→ 回答评测
→ Agent 路由与 Tool 评测
→ 完整任务评测
→ 系统性能评测
```

只看最终回答，无法知道问题发生在哪一层。

## 2. 评测数据格式

```json
{
  "id": "eval_001",
  "question": "为什么 ACTIONS_STEP_DEBUG 没有输出调试日志？",
  "reference_answer": "……",
  "required_facts": [
    "调试日志变量的设置位置",
    "Runner 读取变量的时机"
  ],
  "relevant_doc_ids": [
    "github_actions_zh_actions__how-tos__monitor-workflows__enable-debug-logging"
  ],
  "forbidden_doc_ids": [],
  "expected_route": "knowledge",
  "expected_tool_calls": [],
  "should_answer": true,
  "tags": ["multi_document", "refund"]
}
```

`relevant_doc_ids` 必须人工审核，否则 Recall 没有可信分母。

## 3. 检索评测单位

Baseline 冻结为：

```text
Retriever 返回：Chunk
Ground Truth：relevant_doc_ids
Top-K 返回 Chunk；命中按唯一 relevant Parent Document 计数
Citation：保留具体 chunk_id、parent_doc_id、section_path 和 source_url
```

同一 Parent Document 的多个 Chunk 只能贡献一次命中，但仍占用 Top-K 名额。文档级指标不能识别“命中文档但命错章节”的问题，因此逐题结果仍要保存 Chunk，并在失败分析中人工检查；必要时后续增加 `relevant_chunk_ids`，不与 Baseline 同时改变。

## 4. 数据集阶段

### Smoke Set：12 条

阶段 1 验证导入、检索、引用和拒答程序能跑。

### Dev Set：阶段 2 为 30 条，阶段 6 扩展到 60 条

用于调参和失败分析。

### Test Set：30 条

最终方案确定后运行，不能反复看着它调参数。

覆盖：

- 直接事实；
- 同义表达；
- 错误码；
- 多文档；
- 版本冲突；
- 无答案；
- 模糊问题；
- Tool；
- 高风险动作；
- Prompt Injection。

## 5. 检索指标

### Recall@K：召回率/查全率

```text
Top-K Chunk 覆盖的唯一正确 Parent Document 数 / 全部正确 Parent Document 数
```

回答：正确证据是否找全。

### Precision@K：查准率

```text
Top-K Chunk 覆盖的唯一正确 Parent Document 数 / K
```

回答：返回候选有多少是有用的。

### MRR

关注第一个 `parent_doc_id` 属于 Ground Truth 的 Chunk 排名。同一文档后续重复 Chunk 不产生额外命中。

`GITHUB_TOKEN`、`ACTIONS_STEP_DEBUG`、YAML Key 等精确标识符场景通常希望正确文档排在前面，而不是仅仅存在于 Top-20。

### nDCG

当文档相关程度有 0/1/2/3 等级时使用，第一版可以后补。

## 6. 回答指标

- Answer Correctness：是否符合参考答案；
- Faithfulness/Groundedness：说法是否有检索证据支持；
- Answer Relevance：是否回答了问题；
- Citation Correctness：引用是否支持结论；
- Refusal Accuracy：无答案时是否正确拒答。

规则指标优先，LLM Judge 补充。Judge 结果必须人工抽查。

## 7. Agent 指标

- Route Accuracy；
- Tool Selection Accuracy；
- Tool Arguments Valid Rate；
- Unnecessary Tool Call Rate；
- Human Review Required Accuracy；
- Task Success Rate；
- Max Steps Violation；
- Retry Count。

## 8. 系统指标

- P50/P95 延迟；
- Prompt/Completion Token；
- Embedding 延迟；
- Retriever 延迟；
- Reranker 延迟；
- Tool 成功率；
- 错误率；
- 单次请求成本。

## 9. Baseline 配置

```yaml
dataset_version: github-actions-zh-2026-08-05-v1
chunk_strategy: structure_then_recursive
chunk_size: 600
chunk_overlap: 80
embedding_model: BAAI/bge-small-zh-v1.5
retrieval_mode: dense
top_k: 5
candidate_top_n: 5
query_rewrite: false
reranker: null
answer_temperature: 0
```

Baseline 必须先保存逐题结果，之后才能说“优化”。

## 10. 实验顺序

### 实验 A：Chunk

固定其他参数：

```text
300/50
600/80
900/120
```

目标：找到对文档结构最合适的切片。

### 实验 B：top_k

```text
2 / 5 / 10 / 20
```

查看 Recall、Precision、Token 和回答质量。

### 实验 C：Query Rewrite

比较：

```text
original_query
rewritten_query
```

必须评估：

- Recall/Precision 变化；
- `owner/repo`、`run_id`、环境变量、Runner Label 和 YAML Key 是否保留；
- 是否加入虚构信息；
- 额外延迟。

策略建议：第一次检索先使用原问题；如果问题明显依赖多轮上下文或第一次召回不足，再改写。这样减少无意义的 LLM 调用。

### 实验 D：BM25 / Dense / Hybrid

按标签分别看：

- `exact_term`；
- `semantic_paraphrase`；
- `multi_document`。

环境变量、YAML Key 和精确 API 名预期 BM25 更强；自然语言改写预期 Dense 更强；是否使用 Hybrid 由标签结果决定。

### 实验 E：Embedding

固定 Chunk、检索方式和 top_k，只换：

```text
bge-small-zh-v1.5
bge-m3
```

记录质量、索引耗时、内存和延迟。

### 实验 F：Reranker

```text
Hybrid 召回 candidate_top_n=20
→ Reranker
→ 最终 context_top_k=5
```

先确认 Recall@20 足够高，再看 Reranker 是否提高 Precision/MRR。

## 11. 为什么不能同时改多个变量

如果同时：

```text
换模型
改 Chunk
改 top_k
开 Query Rewrite
加 Reranker
```

即使分数提高，也不知道原因，无法形成工程判断。

正确方式：

```text
一次只改变一个主要因素
→ 保存配置
→ 运行同一数据集
→ 比较差异
→ 分析失败样例
→ 记录决策
```

## 13. 如何查看结果

### 本地

- CSV：逐题查看；
- JSON：保留完整结构；
- Markdown Report：写入 README；
- Pandas：聚合标签和实验。

### LangSmith

- Dataset；
- Experiment；
- Evaluator；
- 每条 Trace；
- 多版本对比。

平台帮助展示，不替代 Ground Truth 和指标理解。

## 14. 调试决策树

```text
Recall 低
→ 查导入、Chunk、Embedding、Query、top_k、Hybrid

Recall 高但 Precision 低
→ 查噪声、重复、top_k、Reranker、metadata filter

Recall/Precision 都不错但答案错
→ 查 Prompt、证据冲突、Answer Model、Context 格式

Faithfulness 低
→ 加证据限制、拒答、引用验证

Tool 路由错
→ 查意图 Schema、规则优先、边界样例

延迟高
→ 查重复 Embedding、Query Rewrite、candidate_top_n、Reranker、模型
```

## 15. 最终选择不是最高分

需要综合：

```text
质量
延迟
成本
内存
索引时间
复杂度
可维护性
```

例如：强模型 Recall 只提高 1%，但延迟增加 4 倍，可以保留轻量模型。

## 16. 调优完成标准

- 有 Baseline；
- 有固定 Dev/Test Set；
- 有至少三类实验；
- 每次只改变一个主要变量；
- 有逐题失败分析；
- 有最终方案与放弃方案；
- 有质量/延迟/成本权衡；
- 有回归评测防止后续退化。
