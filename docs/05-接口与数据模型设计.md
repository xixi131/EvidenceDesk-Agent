# 05｜接口与数据模型设计

## 1. API 设计原则

- 使用 `/api/v1` 版本前缀；
- 请求和响应使用 Pydantic；
- API Schema 不直接复用 SQLAlchemy Model；
- 所有请求有 `request_id`；
- 会话请求有 `thread_id`；
- 长任务返回任务 ID；
- 错误结构统一；
- 写操作考虑幂等。

## 2. 统一响应

成功：

```json
{
  "ok": true,
  "data": {},
  "error": null,
  "meta": {
    "request_id": "req_001",
    "timestamp": "2026-08-05T12:00:00+08:00"
  }
}
```

失败：

```json
{
  "ok": false,
  "data": null,
  "error": {
    "code": "VECTOR_STORE_UNAVAILABLE",
    "message": "知识检索服务暂时不可用",
    "details": null,
    "retryable": true
  },
  "meta": {
    "request_id": "req_001"
  }
}
```

内部日志记录技术异常，外部响应提供安全、稳定的错误码。

## 4. Human Review 接口

### POST `/api/v1/threads/{thread_id}/actions/{action_id}/approve`

请求：

```json
{
  "approved": true,
  "comment": "已确认取消专用演示仓库中的工作流运行"
}
```

要求：

- action_id 必须对应暂停 State；
- 同一个动作不能重复执行；
- 保存审批人、时间和意见；
- 恢复 Graph 时使用已冻结参数。

## 5. GitHub Workflow Tool 接口边界

Tool 由 Agent 内部调用，不直接把 GitHub Token 暴露给模型。

只读：

```text
get_workflow_run(owner, repo, run_id)
list_workflow_jobs(owner, repo, run_id)
```

高风险写操作：

```text
cancel_workflow_run(owner, repo, run_id)
rerun_failed_jobs(owner, repo, run_id)
```

写操作只能通过 Human Review 恢复路径执行。GitHub REST API 固定使用 `https://api.github.com`、`Accept: application/vnd.github+json` 和 `X-GitHub-Api-Version: 2026-03-10`。GitHub API 是 Workflow 实时状态的事实来源，PostgreSQL 只保存本项目的审批、幂等和审计记录。

## 6. 文档接口

### POST `/api/v1/documents/ingest`

第一版支持 multipart 文件或本地开发目录，不接受任意远程 URL，避免 SSRF 和下载安全问题。

第一版在同一请求内同步完成导入，不依赖后台任务队列。返回：

```json
{
  "job_id": "ingest_001",
  "status": "completed",
  "document_count": 33
}
```

### GET `/api/v1/ingestion-jobs/{job_id}`

返回：

```json
{
  "status": "completed",
  "document_id": "doc_001",
  "chunk_count": 42,
  "embedding_model": "BAAI/bge-small-zh-v1.5",
  "duration_ms": 2100
}
```

### DELETE `/api/v1/documents/{document_id}`

第一版采用归档：

```text
PostgreSQL status=archived
Weaviate metadata status=archived 或删除对应 Chunk
```

需要记录审计日志。

## 7. 评测接口

### POST `/api/v1/evaluations/run`

```json
{
  "dataset_version": "dev_v1",
  "config": {
    "chunk_strategy": "recursive_600_80",
    "embedding_model": "BAAI/bge-small-zh-v1.5",
    "retrieval_mode": "dense",
    "top_k": 5,
    "query_rewrite": false,
    "reranker": null
  }
}
```

返回 `evaluation_run_id`，实际运行早期可同步，后续再异步化。

### GET `/api/v1/evaluations/{run_id}`

返回：

- 配置；
- 状态；
- Recall/Precision/MRR；
- Answer 指标；
- 延迟和 Token；
- 失败样例链接。

## 8. Feedback 接口

### POST `/api/v1/feedback`

```json
{
  "request_id": "req_001",
  "thread_id": "thread_001",
  "rating": -1,
  "reason": "引用没有覆盖 Runner 读取变量的时机",
  "expected_answer": "应根据启用调试日志的官方文档说明变量设置位置和生效时机"
}
```

真实失败反馈后续进入回归评测集。

## 10. Weaviate Collection

建议：`KnowledgeChunk`

属性：

```text
chunk_id
parent_doc_id
title
section_path
content
category
product
version
status
effective_at
content_hash
```

向量由应用手动生成和传入，原因：

- 能明确控制 Embedding 模型；
- 方便 A/B 实验；
- 便于记录模型版本；
- 更换模型时知道必须重建索引。

## 11. ID 设计

建议使用 UUID/ULID：

```text
request_id
thread_id
action_id
job_id
run_id
```

业务外部 ID，例如 GitHub `run_id`，不能直接作为本项目数据库主键。`owner/repo/run_id` 作为外部资源标识保存。

## 12. 幂等设计

写操作请求支持：

```text
Idempotency-Key
```

典型：

- 创建工单；
- 取消工作流或重新运行失败 Job；
- 文档导入；
- 恢复审核动作。

重复请求返回原结果，避免 Agent 重试造成重复副作用。

## 13. 接口验收

- OpenAPI 可查看；
- 所有请求 Schema 有示例；
- 错误码稳定；
- request_id 可串联日志；
- 写操作可防重复；
- API 与数据库模型分离；
- 集成测试覆盖成功、校验失败、外部依赖失败。
