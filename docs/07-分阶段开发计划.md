## 0. 如何使用本文

每次开始任务只看两样：`当前检查点` 和 `当前阶段的任务清单 + 阶段门禁`。其余章节按需查。

**验收单位是「阶段」，不是每个子任务。** 子任务只是一个 checklist，帮你不漏步骤；真正决定“能不能往下走”的是阶段末尾那一个门禁。不要给每个子任务单独设关卡、单独写验收记录。

阶段状态标记：

```text
[x] 阶段门禁已通过
[~] 进行中
[ ] 未开始
[!] 真实阻塞
```

一个阶段完成后，在该阶段标题下追加三行即可（模板见第 3 节）：做出了什么、怎么验证的、下一步。

两条底线保留（这是工程可信度，不是仪式）：

```text
1. 代码/文档“已生成”不等于“已完成”，以能跑通的验证为准；
2. 学习进度单独记在持续学习笔记里，不塞进本文，也不阻塞工程进度。
```

## 4. 保持节奏与秩序的规则（精简版）

1. 以「阶段」为推进和验收单位；阶段内的子任务是 checklist，可灵活并行、合并、增删；
2. 一个阶段的门禁没过，不因为对话变长就跳进下一阶段；但允许在阶段内调整子任务顺序；
3. 只有能跑通的验证（文件、命令、测试、运行结果）才改变阶段状态；“已生成”不算；
4. 本文与本地状态冲突时，以本地文件/Git/测试/运行结果为准，并顺手修正本文；
5. 写代码前只需读 3 篇核心：本文（当前检查点）、`02-系统架构` 和当前阶段相关的那一篇主题文档；其余按需查；
6. ADR 只写给「不可逆或代价高」的决策（技术选型、数据冻结、分层）；日常实现选择不写 ADR；
7. 学习进度单独记在持续学习笔记，不进本文，也不作为工程门禁；
8. 每次新对话先读「当前检查点」，从下一步继续。
