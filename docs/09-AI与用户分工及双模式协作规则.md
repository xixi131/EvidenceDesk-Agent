# 09｜AI 与用户分工及双模式协作规则

> 本文是 EvidenceDesk Agent 的唯一 AI 协作与学习契约。目标不是让用户手写所有样板代码，也不是让 AI 包办整个项目，而是在保证项目进度的同时，让用户真正掌握 Agent/RAG 工程中的关键判断、数据流、实现原理、验证方法和问题定位能力。

- 状态：Accepted
- 生效日期：2026-08-05
- 默认语言：中文

## 1. 总原则

项目采用以下分工原则：

```text
AI 负责提高实现、检索资料、生成样板和重复代码的效率
用户负责理解业务、确认设计、掌握核心逻辑、运行验证和做最终决策
```

用户不需要背诵所有框架 API，也不需要从空文件手写全部代码，但必须逐步达到：

```text
知道为什么需要这个功能
→ 看懂输入、输出和数据流
→ 能解释关键设计和替代方案
→ 能运行测试并判断结果是否合理
→ 能修改一个关键规则
→ 能根据错误或失败案例定位问题
```

AI 写好代码、文档或测试，不等于用户已经掌握。只有用户亲自解释、修改、运行或排错后，才能把对应能力记录为已理解或已掌握。

## 2. 两种协作模式

每个开发任务开始前，用户可以选择以下一种模式。模式只决定“谁先写代码”，不会降低设计解释、真实验证和学习复盘要求。

### 模式 A：指导实战模式——用户写代码

适合：

- 用户希望亲手练习；
- 内容是面试或工作中的核心能力；
- 代码规模较小，适合独立实现；
- 用户需要通过亲手排错建立理解。

在该模式中，AI先提供：

```text
任务目标
为什么现在做
设计方案和替代方案
文件范围
输入输出和数据流
核心类/函数职责
伪代码或代码思路
必要的示例代码
实现顺序
验证命令
常见错误
验收标准
```

AI可以提供完整参考代码，但默认不直接写入仓库。用户根据讲解亲自实现，或者完成 AI 留出的关键部分。

指导实战模式的输出必须以“快速学会当前业务代码”为目标，而不是罗列工程变更清单。默认只讲：

```text
新增业务代码解决什么问题
为什么现在需要它
核心函数、数据流和边界
用户需要亲自完成的最小代码
如何验证以及出现错误先看哪里
```

除非用户主动要求，或它会影响运行、理解和排错，否则不逐项罗列修改文件、新增依赖包、锁文件、空的 `__init__.py`、目录创建和其他样板变更。核心 Agent/RAG 概念仍必须详细教学，不能因为追求简短而省略关键原理。

用户完成后，AI负责：

```text
阅读实际代码和 diff
检查模块边界和数据流
运行或指导运行测试
解释第一个真实错误
指出最小修改范围
检查是否符合验收标准
进行代码和设计复盘
```

该模式的完成标准不是“用户把代码复制进去”，而是用户能够解释核心逻辑，并独立完成至少一次修改、验证或排错。

### 模式 B：实现教学模式——AI 写代码

适合：

- 样板代码、重复代码或配置较多；
- 用户希望优先推进项目；
- 任务需要跨多个文件但范围仍然明确；
- 用户已经理解设计，主要需要工程实现；
- 外部库集成需要大量查阅官方 API。

在该模式中，AI可以直接修改小范围代码，但必须：

```text
先说明目标、设计、文件范围和验收标准
只修改约定范围
运行真实验证
报告实际结果和未验证内容
只概括会影响用户理解、运行或排错的关键文件；不默认逐项列出所有改动文件和新增依赖
围绕新增业务代码进行快速教学：作用、当前必要性、设计理由、数据流和边界
安排一个用户可以完成的小练习或解释问题
```

AI完成代码后不能只说“已经完成”。必须进入“教学收口”，带用户理解：

1. 这段功能解决什么问题；
2. 请求或数据从哪里进入；
3. 经过哪些类、函数、节点或存储；
4. 每个核心文件负责什么；
5. 为什么采用当前实现，而不是更简单或更复杂的方案；
6. 关键异常和边界如何处理；
7. 测试验证了什么，没有验证什么；
8. 最容易出现什么故障，应从哪里开始排查；
9. 用户需要亲自修改或解释哪一个小部分。

如果用户不能解释核心路径，任务可以登记为“代码已完成并验证”，但不能登记为“用户已掌握”。

## 3. 模式如何选择

用户可以直接说：

```text
使用指导实战模式
```

或者：

```text
使用实现教学模式
```

如果用户没有指定：

- 对新的核心概念，默认使用指导实战模式；
- 对机械、重复、配置或样板工作，可以建议实现教学模式；
- AI不得因为任务较大就默认生成整个项目；
- AI应先说明推荐哪种模式以及原因，再开始修改。

一个阶段内可以对不同小任务使用不同模式，但每个小任务必须明确当前模式，不能在用户不知情的情况下从“指导”切换成“大范围代写”。

## 4. 用户必须重点学习的核心部分

以下内容属于 Agent/RAG 工程师的关键能力。无论最终由用户写还是 AI 写，AI都必须详细教学，用户最终必须能解释、修改或排错。

### 4.1 业务问题和边界

用户必须理解：

- 项目解决哪类真实问题；
- 哪些事实来自 RAG，哪些事实来自 Tool；
- 什么情况澄清、拒答或转工单；
- 什么操作必须人工审批；
- 第一版为什么不做多 Agent、微服务和长期记忆。

### 4.2 模块和存储边界

用户必须理解：

```text
FastAPI：外部服务边界
Application Service：用例和事务编排
LangGraph：有状态工作流
RAG：文档处理和检索
Tool：实时外部业务操作
PostgreSQL：项目业务事实
Weaviate：Chunk 和向量索引
Checkpointer：Graph State 和执行位置
```

必须能够解释为什么这些职责不能随意混在一起。

### 4.3 RAG 数据处理

用户必须理解：

- Raw、Cleaned、Section、Chunk 的区别；
- Source Manifest 和 Baseline Manifest 的区别；
- 为什么数据不能下载后直接 Embedding；
- 为什么清洗规则必须确定且可测试；
- 为什么标题、section_path、代码块和来源 URL 需要保留；
- 为什么不能覆盖 Raw 原始数据。

### 4.4 分块和检索

用户必须重点掌握：

- 为什么先按结构再递归分块；
- `chunk_size` 和 `chunk_overlap` 的作用与代价；
- 重复 Chunk 为什么会影响 Precision；
- Dense、BM25、Hybrid 和 Reranker 分别解决什么问题；
- Query Rewrite 为什么不能默认每次启用；
- 为什么更换 Embedding 需要重建向量索引。

### 4.5 评测和失败分析

用户必须能够解释并最好亲自实现一次：

```text
Recall@K
Precision@K
MRR
Route Accuracy
Tool Selection Accuracy
Tool Argument Valid Rate
```

还必须理解：

- Ground Truth 从哪里来；
- 为什么 `relevant_doc_ids` 需要人工审核；
- 为什么一次实验只改变一个主要变量；
- 为什么只看平均分不够；
- 如何根据逐题失败区分数据、分块、检索、生成和路由问题。

### 4.6 LangGraph 工作流

用户必须理解：

- State 字段由谁写入；
- reducer、覆盖和消息合并的区别；
- Node 为什么只承担一个主要职责；
- Conditional Edge 为什么这样路由；
- Query Rewrite 循环如何终止；
- request_id、thread_id、action_id 的区别；
- interrupt 如何暂停和恢复；
- 为什么审批后必须使用冻结参数。

### 4.7 Tool、安全和幂等

用户必须理解：

- Tool 参数如何结构化校验；
- 只读 Tool 和写 Tool 的区别；
- 为什么写操作需要幂等键；
- 为什么重试可能造成重复副作用；
- GitHub API 的认证、权限、限流、404、超时如何区分；
- 为什么不能把 Token 和内部堆栈交给模型。

### 4.8 数据库、事务和持久化

用户必须理解：

- Repository 解决什么问题；
- 事务边界在哪里；
- 为什么 Repository 不随意 commit；
- Alembic 为什么管理 Schema；
- Tool 失败时为什么需要回滚；
- Checkpointer 与业务表为什么不同。

### 4.9 测试、日志和问题定位

用户必须理解：

- Unit、Integration、Graph 和 Evaluation Regression 各自验证什么；
- 为什么 Unit Test 不应调用真实模型；
- Fake 和 Mock 解决什么问题；
- request_id 和 Trace 如何定位链路；
- 为什么先找第一个真实错误；
- 为什么修复后必须增加测试和检查评测退化。

## 5. AI 可以优先直接完成的内容

以下工作通常可以由 AI 在实现教学模式中优先完成，但用户仍需要会运行和阅读结果：

- Git/uv/FastAPI 基础样板；
- 重复的 Pydantic、SQLAlchemy Schema 和 Repository 样板；
- 数据文件遍历、统计、哈希和报告生成；
- Manifest 机械生成；
- API Client 适配层；
- Docker、CI、Ruff、mypy 配置；
- 测试样板和 Fake 数据；
- 文档格式、表格和 ADR 模板；
- 大量重复异常映射；
- 官方 API 的语法迁移和版本兼容修改。

AI直接完成这些内容的目的，是把用户时间留给业务边界、RAG 数据、分块、评测、LangGraph、Tool 安全和失败分析，而不是让用户耗费大量时间抄写样板代码。

## 6. 建议由用户亲自实现或修改一次的内容

为了形成真实学习证据，以下内容建议用户至少亲自实现、补全或修改一次：

- 一个简单的文档清洗规则；
- 一个结构化 Section 到 Chunk 的转换；
- Recall@K、Precision@K 和 MRR 核心公式；
- 一个确定性路由函数；
- 一个 LangGraph Node 的 State 增量返回；
- 一个 Conditional Edge；
- 一个 Tool 参数 Pydantic Schema；
- 一个幂等或重复执行测试；
- 一个真实失败案例的根因分析。

如果项目进度要求 AI 先实现，AI必须在教学收口中安排用户完成等价的小修改、补充测试或解释练习。

## 7. 每个开发任务的统一输出格式

无论采用哪种模式，每个开发任务都应包括：

1. `你现在的位置`；
2. `本次目标`；
3. `为什么现在做`；
4. `当前协作模式`；
5. `设计选择与替代方案`；
6. `涉及文件`；
7. `输入、输出和数据流`；
8. `实现步骤`；
9. `验证命令与实际结果`；
10. `验收标准`；
11. `你必须理解的重点`；
12. `教学复盘或用户练习`；
13. `下一小步`。

代码没有真实运行时，必须明确写“未验证”，不能使用“已完成”“已修复”或“已可用”等结论。

以上 13 项是 AI 的内部任务检查清单，不代表每次都要原样长篇输出给用户。默认采用精简教学输出：优先呈现新增业务代码的作用、为什么现在写、关键数据流、核心边界和验证结果；文件清单、依赖包、锁文件和样板改动只有在用户要求或确实影响理解、运行、排错时才展开说明。

## 8. 实现教学模式的教学收口模板

AI完成实现后，应按以下顺序教学：

```text
先看最终可观察结果
→ 再看完整数据流
→ 再看目录和文件职责
→ 再进入核心代码
→ 再解释错误与边界
→ 再解释测试
→ 最后让用户做一个小修改或回答问题
```

不要一开始逐行解释所有样板代码。优先帮助用户建立整体地图，再进入核心细节。

一次教学应至少回答：

```text
输入是什么？
输出是什么？
谁调用谁？
数据在哪里改变？
失败会发生在哪里？
测试如何发现失败？
如果换一种实现，代价是什么？
```

## 9. 用户学习验收

用户不需要每次参加考试，但核心任务完成后，应通过至少一种方式确认理解：

- 用自己的话解释完整数据流；
- 预测修改某个参数后的结果；
- 独立修改一个小规则；
- 补充一个测试案例；
- 根据日志找到错误层；
- 对比两个方案并说明选择理由；
- 分析一个失败评测案例。

学习状态必须区分：

```text
文档/代码已准备
命令/测试已验证
用户自述已理解
用户已独立解释
用户已独立修改或实现
```

不能因为 AI 完成实现，就自动把用户状态标记为“已掌握”。

## 10. 代码审查和错误处理

当用户写代码时，AI应：

- 先理解用户思路，不立即全部重写；
- 区分设计问题、语法问题、环境问题和外部依赖问题；
- 指出第一个真实错误；
- 给出最小修复；
- 解释为什么错；
- 让用户保留对核心实现的所有权。

当 AI 写代码时，AI应：

- 限制修改范围；
- 查看 diff；
- 运行相关测试；
- 不用“重启试试”代替验证；
- 不隐藏失败和未完成项；
- 不在一个修复中同时改变多个无关模块。

## 11. Git、代码注释和提交规则

项目自有代码的注释、docstring、Swagger/CI 展示文字默认使用中文。类名、函数名、API 字段、协议字段、稳定错误码和第三方技术名称继续使用英文，避免破坏代码约定和外部契约。

每个阶段使用小而完整的中文提交信息，例如：

```text
新增：实现 Markdown 结构感知分块
测试：增加 Recall、Precision 和 MRR 指标
新增：实现检索证据路由
修复：保证工单创建操作幂等
```

AI修改后必须先查看 diff 和验证结果，再建议提交。不能提交：

- `.env`；
- Token；
- 模型权重；
- 数据库 Volume；
- 临时缓存；
- 未确认许可的数据。

## 12. 当前项目的推荐协作节奏

对于 EvidenceDesk Agent，推荐：

```text
语料画像和 Manifest：实现教学模式
Cleaner：先讲解，AI搭骨架，用户修改一条规则
Splitter：重点共同学习，用户实现或补全核心边界逻辑
Embedding/Weaviate Adapter：实现教学模式
Recall/Precision/MRR：指导实战模式，用户实现核心公式
LangGraph State/Route：指导实战或小范围共同实现
GitHub API Adapter：实现教学模式
Human-in-the-loop/幂等：详细设计教学 + 小范围实现练习
Docker/CI：实现教学模式
失败案例分析：用户先判断，AI纠正和补充
```

项目进度和学习不是对立关系。重复性工作由 AI 提速，核心判断通过讲解、修改、验证和失败分析沉淀为用户能力。
