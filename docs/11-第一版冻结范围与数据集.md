# 11｜第一版冻结范围与数据集

> 本文是 EvidenceDesk Agent 第一版业务语境、知识库数据、Tool 边界和 RAG Baseline 的冻结说明。其他文档与本文冲突时，以本文和对应 ADR 为准，并应尽快同步修正。

- 决策状态：Accepted
- 冻结日期：2026-08-05
- 项目名称：EvidenceDesk Agent
- 第一版产品语境：GitHub Actions 技术支持与工作流运行协同

## 1. 第一版到底做什么

EvidenceDesk Agent 第一版服务于使用 GitHub Actions 的开发者和运维人员，处理：

1. 工作流语法、上下文、表达式、变量、缓存、构件、权限和密钥等知识问题；
2. 工作流失败、日志、调试、自托管 Runner 等故障排查问题；
3. 查询真实工作流运行和 Job 状态；
4. 证据不足时澄清、拒答或创建本地支持工单；
5. 取消运行、重新运行失败 Job 等有副作用操作必须暂停并人工审核；
6. 使用固定评测集验证检索、路由、Tool 参数和最终回答。

本项目不是 GitHub 官方产品，也不代表 GitHub 提供支持服务。

## 2. 统一业务流程

```text
用户问题
→ 意图分类
├── GitHub Actions 知识问题
│   → 首次使用原始问题做 Dense Retrieval
│   → 判断证据
│   → 证据不足且允许重试时再 Query Rewrite
│   → 有证据则带引用回答
│   → 无法解决则澄清、拒答或创建支持工单
├── 工作流实时查询
│   → GitHub REST API 只读 Tool
│   → 根据真实返回回答
└── 工作流写操作
    → 冻结 owner/repo/run_id/action
    → LangGraph interrupt
    → 人工批准
    → 在专用演示仓库执行
    → 保存审计和幂等记录
```

## 3. 冻结的 Tool

### 3.1 只读 Tool

```text
get_workflow_run(owner, repo, run_id)
list_workflow_jobs(owner, repo, run_id)
```

数据来源：GitHub REST API。固定 API 配置：

```text
base_url=https://api.github.com
X-GitHub-Api-Version=2026-03-10
Accept=application/vnd.github+json
```

阶段 4 的公开只读 Smoke Target 冻结为：

```text
owner=github
repo=docs
run_id=30964320373
expected_run_name=CodeQL analysis
expected_job_name=build
```

该历史运行已在 2026-08-05 真实读取成功。若 GitHub 后续清理历史运行，允许在不改变业务设计的情况下更新 Smoke Target，并记录变更。单元测试和 CI 使用 Fake GitHub Gateway，不依赖网络和 Token。

### 3.2 本地业务写 Tool

```text
create_support_ticket(thread_id, title, description, agent_context)
```

数据来源：PostgreSQL。

要求：显式升级条件、幂等键、事务、审计。创建支持工单有副作用，但不属于破坏性高风险操作；如果是 Agent 主动建议升级，应先获得用户确认。

### 3.3 高风险外部写 Tool

```text
cancel_workflow_run(owner, repo, run_id)
rerun_failed_jobs(owner, repo, run_id)
```

要求：

- 必须 Human-in-the-loop；
- 审批前冻结参数；
- 使用 action_id 和 idempotency_key；
- 只允许在用户控制的 `evidence-desk-actions-demo` 专用演示仓库运行；
- 不允许对生产仓库执行项目验收；
- 没有有效 Token 时只能完成 Fake/离线验证，不能宣称真实写操作已验证。

### 4.2 为什么下载渲染后的页面 Markdown

GitHub Docs 源仓库中的 Markdown 包含可复用片段和模板语法。第一版从官方文档页面接口保存已经渲染的 Markdown，避免把未展开的模板标记当作知识内容，同时保留标题、列表、代码块和章节结构。


### 4.3 Source Dataset 与 Chinese Baseline

33 篇 Raw Source 全部保留。数据画像发现 4 篇参考页正文以英文为主，且占原始字符量约 70%，因此第一次中文 Embedding Baseline 只选择 29 篇：

```text
Source Manifest：记录33篇原始快照
Baseline Manifest：记录29篇纳入、4篇暂时排除和每篇风险
```

暂时排除的 4 篇不删除，留作 `github-actions-multilingual-reference-v1` 实验。完整规则见 `docs/12-语料审阅与清洗规则.md` 和 ADR-002。

验证命令：

```bash
python3 scripts/build_github_actions_baseline_manifest.py
python3 scripts/verify_baseline_manifest.py
```

### 4.4 第一版文档类型

第一版只支持并验收 Markdown。

TXT、PDF Loader 从第一版必需项移出，原因是固定数据源本身就是结构化 Markdown。为了满足“至少两种格式”而人为转换 PDF，不会增加当前检索实验的真实性，只会扩大解析范围。后续只有在引入真实 PDF 数据源时才增加 PDF Loader 和对应评测。

## 5. 冻结的 RAG Baseline

```yaml
strategy: structure_then_recursive
chunk_size: 600
chunk_overlap: 80
length_unit: character
keep_title: true
keep_section_path: true
embedding_model: BAAI/bge-small-zh-v1.5
retrieval_mode: dense
top_k: 5
candidate_top_n: 5
query_rewrite: false
reranker: null
answer_temperature: 0
```

这些参数是实验起点，不是最终最佳值。第一次检索必须使用原始问题；Query Rewrite 只能在后续实验或证据不足重试路径中启用。

## 6. 检索与引用的评测单位

Baseline 统一采用：

```text
检索执行单位：Chunk
Ground Truth 单位：Parent Document
指标输入：Top-K Chunk；命中按唯一 relevant Parent Document 计数
引用单位：Chunk + Parent Document + 原始页面 URL
```

同一 Parent Document 的多个 Chunk 出现在 Top-K 时，只能贡献一次命中。`Recall@K = 唯一正确 Parent Document 命中数 / 全部正确 Parent Document 数`；`Precision@K = 唯一正确 Parent Document 命中数 / K`；MRR 使用第一个 `parent_doc_id` 属于 Ground Truth 的 Chunk 排名。重复 Chunk 会占用 K，从而自然降低 Precision，而不会虚增命中。

如果后续发现“文档命中了但章节错误”无法被文档级指标识别，再新增人工审核的 `relevant_chunk_ids` 辅助指标，不在 Baseline 阶段同时引入。

## 7. 固定评测集规模

### 阶段 1

```text
Smoke Set：12 条
```

只验证导入、检索、引用和拒答链路能运行。

### 阶段 2

```text
Dev Set：30 条人工审核问题
```

用于 Chunk 和 top_k 第一轮实验。

### 阶段 6

```text
Dev Set：扩展到 60 条
Test Set：30 条，最终方案确定前不反复查看
```

覆盖标签：

```text
cache_and_artifact

multi_document

no_answer

business_write
human_review

```

## 8. 文档导入执行方式

第一版不引入 Celery、Redis 或独立任务队列。

```text
POST /api/v1/documents/ingest
→ PostgreSQL 创建 ingestion_job
→ 同一请求内同步执行解析、分块、Embedding 和 Weaviate upsert
→ 更新 completed/failed
→ 返回最终任务状态和 job_id
```

`GET /api/v1/ingestion-jobs/{job_id}` 继续保留，用于查询历史结果。未来只有在真实导入耗时需要脱离请求生命周期时，才新增外部任务执行器。

## 9. 阶段顺序

```text
阶段 0：Git、uv、FastAPI 骨架、配置、测试、日志、Compose、CI
阶段 1：最小 PostgreSQL 文档表 + Alembic + Markdown 导入 + Dense RAG Baseline
阶段 2：文档级 Recall/Precision/MRR 和 Chunk/top_k 实验
阶段 3：LangGraph 路由、证据判断、有限 Query Rewrite、Fake Tool
阶段 4：GitHub REST 只读 Tool + PostgreSQL 工单
阶段 5：取消/重跑操作的审批、幂等和 Checkpointer 恢复
阶段 6：Hybrid、Embedding、Reranker、完整 Agent 评测
阶段 7：Docker 与交付收口
```

## 10. 第一版完成时必须能演示

1. 校验 33 篇 Source 文档，并导入 Chinese Baseline 的 29 篇文档；
2. 对工作流故障、缓存、权限和 Runner 问题返回带原始页面 URL 的引用；
3. 对知识库没有覆盖的问题拒答或创建支持工单；
4. 通过 GitHub REST API 查询一次真实公开工作流运行；
5. 取消或重跑操作必经审批，并只在专用演示仓库验证；
6. 展示 Baseline、至少三类实验、逐题失败和最终选择；
7. 从 Trace 解释一次知识、只读 Tool、工单升级和人工审批路径。
